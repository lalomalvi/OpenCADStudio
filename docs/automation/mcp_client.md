# Cliente MCP persistente — M1 y primer corte M2

`mcp_client.py` abre un único proceso `OpenCADStudio --mcp` por instancia, negocia `2026-07-28` con `server/discover`, comprueba Tasks, correlaciona respuestas JSON-RPC por ID aunque lleguen fuera de orden y drena `stderr` sin publicarlo. La cola se limita a 64 solicitudes pendientes. Cada RPC tiene timeout monotónico; los Tasks tienen deadline total. EOF, JSON inválido y respuestas sin estructura fallan cerrado.

El cliente serializa las escrituras al pipe con un candado separado del mapa de solicitudes pendientes. Una escritura bloqueada no retiene el candado que necesita el lector de `stdout` para entregar respuestas; el test sintético demora la respuesta del primer RPC, bloquea la escritura del segundo y verifica que el primero se entregue **antes** de liberar el pipe. Este control es L1 de concurrencia; no afirma que el sistema operativo o un servidor externo nunca puedan bloquear el pipe.

La correlación exige además `id` entero positivo de tipo exacto. El peer sintético envía `true`, `1.0` y `"1"` para una solicitud pendiente con ID `1`; las tres respuestas fallan cerrado. Esto evita que la igualdad `True == 1` de Python asigne una respuesta de ID inválido al slot correcto por accidente.

`ready_session(launch_if_none=True)` consume `absent`, `starting`, `ready` y `failed`; respeta `retry_after_ms`, el deadline y un único intento de lanzamiento. Una sesión ambigua exige `session_id` explícito. El servidor publica PID, ejecutable e instante de creación del proceso obtenido del SO en Windows, sin token. Al conectar la sesión seleccionada, valida el ID hexadecimal, rechaza enlaces en el descriptor y hace un nuevo handshake autenticado. El sondeo inicial usa hasta 16 workers y 250 ms por descriptor. Diez repeticiones locales del binario final con 100 descriptores sintéticos privados dieron p50 1900.45 ms y p95 conservador 1907.2 ms; es una medición de esta máquina, no una garantía de producción.

Todas las llamadas `tool("ocs_execute", ...)` de los harnesses pasan por `mutate`. El cliente exige `request_id`, rechaza reutilizarlo con otro contenido y conserva un journal en memoria. Usa `document_id` y `revision` de la sesión leída. Si se pierde una respuesta, consulta `ocs_read operation` con el mismo ID; jamás reenvía la mutación. El servidor guarda el progreso de `batch` y `run_script` en `automation/batch-journal` del perfil local mediante reemplazo atómico y `sync_all` antes de cada paso. Tras reiniciar solo el proceso MCP, la consulta carga el journal exacto, pregunta por el paso activo en la GUI y continúa con la revisión esperada. Un journal corrupto, una operación no verificable o una revisión cambiada detienen nuevas ediciones. El journal contiene comandos y resultados locales, sin token; no se publica ni se copia a Git. La recuperación tras reinicio de GUI sigue sin aceptar.

`mutate` y `recover` comparten ahora un candado reentrante para serializar la reserva y conciliación de `request_id` entre hilos. Dos llamadas concurrentes con el mismo ID y contenido reciben el mismo resultado después de **una sola** ejecución; una reutilización con contenido distinto sigue fallando. Las lecturas RPC continúan concurrentes. Esta serialización puede hacer esperar otra mutación mientras la primera agota su deadline; evita que un segundo hilo introduzca una edición antes de resolver la primera. Un test con peer sintético de respuesta demorada verifica una sola llamada `ocs_execute`; otro pierde la respuesta y verifica una ejecución y una consulta de operación, sin reenvío.

En `run_script`, `attempted_commands` cuenta respuestas terminales de órdenes intentadas. `successful_commands` excluye la orden fallida. `completed_commands` se conserva como alias histórico del conteo intentado, por compatibilidad; no prueba que todas esas órdenes hayan mutado el documento. El índice `failed_command`, `changes`, revisión y estado deben leerse juntos. Ante un batch fallido, el cliente bloquea conservadoramente nuevas mutaciones de esa sesión aunque el último comando no haya registrado cambios; se puede abrir otra sesión sintética para un ensayo independiente, sin repetir a ciegas una orden incierta. El caso de una única orden inválida muestra `attempted_commands=completed_commands=1`, `successful_commands=0`, `changes=[]` y revisión intacta.

Los tres harnesses `mcp_eval.py`, `mcp_acceptance.py` y `mcp_reconstruction_eval.py` reutilizan el mismo transporte. `mcp_smoke.py` conserva solicitudes JSON crudas para validar el wire format independientemente. `waiting_input` bloquea ediciones posteriores cuando procede de un comando; `close_modal` puede revelar otro modal y exige releer `state`. Los harnesses antiguos aún carecen de política de propiedad/cierre y no se ejecutan contra sesiones de usuario en este corte.

Reproducción L1 sin CAD ni planos privados:

```sh
python -m unittest discover -s docs/automation -p test_mcp_client.py -v
python -m py_compile docs/automation/mcp_client.py docs/automation/mcp_eval.py docs/automation/mcp_acceptance.py docs/automation/mcp_reconstruction_eval.py
cargo test --lib mcp::tests
cargo build --bin OpenCADStudio
python docs/automation/mcp_isolated_smoke.py
```

El fixture `tests/fixtures/mcp_stdio_fake.py` cubre arranque lento, sesiones ambiguas, respuestas fuera de orden, pérdida de respuesta tras un efecto, lote en curso, operación desconocida, modal encadenado, fallo explícito, EOF, JSON inválido y presión en `stderr`. El L2 usa un perfil hijo propio en `target/mcp-isolated`: identifica PID/binario, crea tres entidades sintéticas, audita, guarda DWG verificado, coteja SHA-256 y confirma salida. Los reportes y DWG sintéticos quedan fuera de Git. Los fallos iniciales se conservan como fallos. No se abrió el DWG del usuario.

`shutdown_owned_session` es una operación del servidor, no un `QUIT` genérico. Solo se admite cuando este mismo proceso MCP lanzó la GUI; exige PID, hora de creación del SO, ejecutable y `owned_root` canonicalizado. Relee el estado, rechaza modales, comandos activos, documentos sucios y archivos fuera de esa raíz. La cola de la GUI repite esas comprobaciones inmediatamente antes del cierre. El servidor confirma la salida del proceso hijo y devuelve la misma respuesta al repetir el ID. `mcp_owned_shutdown_smoke.py` comprobó rechazos dirty/foreign y cierre propio L2. La GUI escribe heartbeat local cada dos segundos sin token; Windows valida PID y creación de proceso antes de usar un descriptor y pone en cuarentena un descriptor de proceso confirmado muerto/reutilizado. El descriptor con token nace con DACL protegido para propietario y SYSTEM. Un ACL ampliado se rechaza; si existe un descriptor legado de ID válido con ACL inseguro, el descubrimiento falla antes de lanzar otra GUI. La cuarentena conserva el ACL. Los journals nuevos también nacen privados. Un journal antiguo con ACL heredado más amplio falla cerrado y requiere conciliación supervisada, sin reejecutar mutaciones inciertas. Modalidades adicionales de cierre siguen pendientes.
`close_document` aplica la política explícita `require_saved` solo a una GUI hija del mismo MCP. El backend y la GUI comprueban documento/revisión, ruta guardada dentro de `owned_root`, ausencia de modal/comando y que la pestaña no esté sucia. El L2 `mcp_owned_shutdown_smoke.py` rechazó dirty/foreign, cerró solo la pestaña sintética y luego cerró la GUI. No hay política de descarte automático.

`mcp_journal_restart_smoke.py` conserva la GUI sintética, corta el proceso MCP con el primer paso aún en curso, inicia otro MCP en el mismo perfil, consulta el lote por ID y confirma tres entidades en el DWG verificado. No recupera sesiones ajenas ni presupone que una GUI reiniciada preserve operaciones en memoria. Los directorios de fallos anteriores se conservan aparte.

`mcp_gui_loss_smoke.py` cubre el caso distinto de pérdida de la GUI hija propia. Tras respuesta `running` y journal durable de un lote sintético, termina esa GUI, consulta la operación una vez y verifica que el cliente bloquee una mutación posterior sin enviarla. El resultado L2 es `passed_fail_closed`, documentado en [M1-PERDIDA-GUI-SINTETICA-V1.md](masterplan/M1-PERDIDA-GUI-SINTETICA-V1.md). No se ha aceptado recuperación completa ni continuación automática tras reiniciar la GUI.

El cliente acepta `trace_path` y `run_id` opcionales juntos. Crea un JSONL nuevo por run y anexa eventos RPC con método de lista blanca, estado, timestamps UTC y duración monotónica. No serializa argumentos, resultados ni texto de error. `trace.failed` señala cualquier fallo de escritura; el L2 de cierre propio confirma 27 eventos sin campo token. Estos tiempos cubren la espera de transporte observada por el cliente, no tiempos separados de modelo, CAD o render.

`capture_artifact` exige documento y revisiones de geometría/cámara obtenidos de `ocs_read state`. El servidor transmite esos valores a la GUI, verifica que coincidan al terminar la captura y mantiene la respuesta MCP `content` de tipo imagen; añade metadatos estructurados sin Base64. El cliente decodifica una sola imagen PNG acotada a un archivo nuevo del run y registra solo su `ArtifactRef` (hash, tamaño, dimensiones, documento y revisiones). El L2 sintético obtuvo 1024×506 y selló la referencia. La GUI espera un frame codificado por el shader **después de iniciarse la captura** y con las revisiones solicitadas; solo entonces solicita el screenshot. Servidor y cliente verifican `rendered_geometry_revision`, `rendered_camera_revision` y `render_fence=shader_encoded_frame`. Un temporizador acotado a ocho segundos falla incluso si la ventana minimizada no emite frames. El L2 de este corte mostró geometría sintética visible con revisiones 13/0 coincidentes. Esto no prueba inspección visual de todos los elementos ni un readback GPU independiente. El recorte puede incluir texto de la interfaz, por lo que el PNG permanece fuera de Git.

## Checkpoint con presupuesto acotado (M3.6 parcial)

`mcp_budgeted_run.py` acepta una lista fija de comandos, una sesión seleccionada y un `run_id` estable. Aplica límites de pasos y segundos por invocación. Antes de cada `run_script` de un comando anexa y sincroniza una intención con `request_id` determinista y hash del comando; después de una respuesta completada anexa la revisión del documento. El JSONL no guarda comandos ni parámetros privados. Al reanudar con el mismo plan y sesión, verifica cadena/hash y documento/revisión; un paso con intención pendiente se consulta por `ocs_read operation` mediante `Client.recover`, sin reenvío. La discrepancia o resultado incierto detienen el run. Una pausa por presupuesto deja `next_step` y la secuencia puede continuar desde allí.

El L2 `mcp_budgeted_run_smoke.py` pausó tras una línea, cerró solo el proceso MCP, abrió otro proceso MCP con la misma GUI/perfil aislados y completó la segunda línea: consulta por entidades encontró exactamente dos y `save_verified` reabrió el DWG sintético. El checkpoint y DWG están en `target/mcp-isolated`, no en Git. Esta versión cubre presupuesto de pasos y tiempo de comandos; faltan cuotas de tokens/capturas/bytes, identidad del modelo y reanudación de un turno generador completo. No recupera automáticamente un proceso GUI perdido.
