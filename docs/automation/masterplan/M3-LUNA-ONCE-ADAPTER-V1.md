# M3/M7 — creación única de respuesta Luna v1

`luna_once_adapter.request_luna_once` conecta una intención pendiente exacta del `TrialJournal` con un único POST a [Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) para `gpt-6-luna`. El modelo admite imagen de entrada y razonamiento configurado según su [ficha oficial](https://developers.openai.com/api/docs/models/gpt-6-luna); la [guía de visión](https://developers.openai.com/api/docs/guides/images-vision) admite una URL de datos Base64 para PNG/JPEG.

El journal devuelve hashes congelados de imagen, protocolo y binario después de sincronizar la intención. El adaptador exige `verify_pending` para el mismo brazo/caso/repetición/request ID y compara esos hashes, rutas, modelo y esfuerzo antes de leer entradas. Vuelve a hashear exactamente los bytes de imagen/protocolo que enviará; conserva el protocolo UTF-8 byte a byte, incluido CRLF de Windows. Convierte la imagen a Base64 **solo en memoria** para la solicitud. La petición fija `store=false`, `stream=false`, detalle de imagen `original` y presupuesto explícito de salida. El transporte HTTPS estándar emite un POST, con timeout de 120 s, sin redirecciones ni reintento automático. No escribe clave, imagen, prompt ni salida en los archivos del run.

`DirectResponsesClient()` exige `OPENAI_API_KEY` al construirse y debe crearse **antes** de `run_once`, así la falta de acceso no consume una casilla. `request_luna_once` requiere ese cliente inyectado y devuelve en memoria el JSON de respuesta; el callback debe extraer PlanSpec, ejecutar CAD y supervisor, y pasar los objetos directos a `Observation` para el recibo M3. Ese callback completo aún no existe. Cualquier excepción tras `reserve`, incluso timeout o respuesta malformada, se consume como `uncertain` por `run_once`; no se repite una mutación con ID nuevo. El host carece de esa variable y el SDK global `openai 2.15.0` no importa por dependencia `distro` ausente; se usó `urllib` sin tocar AppData. No hubo solicitud real ni imagen reservada.

Evidencia L0: pruebas con transporte falso verifican intención previa, una llamada, bytes/hash de entradas congeladas, modelo/esfuerzo, salida privada ausente del sobre, rechazo por cliente con reintentos, solicitud sin intención y hash falsificado, POST único y fallo HTTP sin repetición. Una prueba inicialmente supuso LF; el protocolo real sintético en Windows conservaba CRLF. La aserción final coteja los bytes enviados y no normaliza el fixture. L3/G0/G10, supervisor/CAD integrado y evaluación de seis imágenes permanecen pendientes.
